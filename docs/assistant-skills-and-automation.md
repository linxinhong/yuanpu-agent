# 助理默认技能与内部自动化

状态：实施设计，2026-09-26。与[助理总体设计](assistant-memory-proposal.md)及 `.tasks/tasks.yaml` 配套。本轮只覆盖本地与企业微信；助理跟随 App 运行。

## 核心分工

`packages/yuanpu-assistant` 自己决定何时观察、整理、复盘、委派和联系用户。它的技能负责**如何判断和表达**，内部自动化负责**何时运行、读取哪些材料、怎样记账和恢复**。技能的自然语言指令不能授予来源读取、文件写入、发消息或调用专业工具的权限；这些能力必须由助理执行环境与宿主接口限定。

`SOUL.md` 是助理长期身份与基本关系，不作为某个定时任务的技能。助理自己的 `skills/` 只装以下默认技能，专业技能留在工作/子代理环境。运行中的技能可根据任务按需装载；不把七份全文永久塞入每轮提示词。

| 默认技能目录 | 何时使用 | 产出与边界 |
| --- | --- | --- |
| `understand-user/` | 用户直接对助理表达想法、偏好或纠正；工作材料反复出现有关线索 | 提出对兴趣、爱好、经历、知识、观点、目标和协作方式的候选理解。标注“明确说过 / 观察到 / 推断”、情境与来源；不凭单次对话诊断人格或能力。 |
| `review-work/` | 工作回合、运行终态或产物变化 | 对照用户目标、约束、实际工具结果和产物，形成完成、部分完成、失败或待核实的证据化评估。评估工作内容，不给用户能力打分；不能只凭模型自述判定完成。 |
| `maintain-memory/` | 有新的可靠认识、用户纠正或删除来源 | 合并、修订、归档 `USER.md`、`MEMORY.md` 及专题笔记，控制摘要预算。用户明确纠正优先；遗忘覆盖索引、历史和衍生内容。只维护记忆，不制定外部执行权限。 |
| `organize-work/` | 评估后出现进展、决定、阻碍或承诺 | 更新 `work/` 的当前关注、项目状态和承诺；区分事实、已决定任务、助理建议与等待核实项。不能把建议写成用户承诺。 |
| `follow-up/` | 期限接近、依赖变化、长期未核实事项需要检查 | 发现未闭环事项，先核对最新证据，必要时提出一次清楚的跟进；沉默不等于完成。仅改变助理台账或生成建议，不自行发送外部消息。 |
| `delegate-and-verify/` | 需要专业技能、文件检查或来源核验 | 写最小必要的委派说明、完成条件与已有授权范围，等待子代理结果，核对证据并决定下一步。同一任务可续聊，新任务独立；子代理不能改助理身份、技能和记忆。 |
| `reflect-and-suggest/` | 每日/每周回顾，或多个工作结论出现值得提醒的联系 | 综合近期变化、长期目标和用户反馈，形成可忽略、可稍后的建议。无新证据时保持安静，建议只出现在助理侧。 |

这些是产品职责，不是七个必须顺序调用的模型步骤。一次回合可先用规则判定“无持久价值”，直接结束；一次工作评估可更新台账而不修改用户画像。默认技能作为 `yuanpu-assistant` 的版本化资源随包发布，首次复制到 `~/.yuanpu/assistant/skills/`。后续版本更新不得覆盖用户编辑；记录内置版本与本地版本，冲突时保留本地文件并提供可审阅差异。新安装或用户自建的助理技能也只能使用助理允许的接口，不能借安装技能自动打开工作 Agent 的工具和扩展发现。

## 内部自动化属于助理运行层

助理有自己的 `automation/` 模块与 `state.sqlite` 工作队列，不把这些周期性检查伪装成用户创建的 `workflows/automation.sqlite` 计划。两者可以复用纯时间计算或调度原语，但不共享任务表、执行实例、身份或通知规则。队列由唯一 Assistant Worker 写入；宿主向它送入已经验证的来源事件，Worker 统一安排后台工作。

| 触发 | 后台动作 | 何时结束 |
| --- | --- | --- |
| `WorkTurnCommitted` / 工作 run 终态 / 产物版本变化 | 收集来源 → `review-work` → `organize-work`，有可靠用户线索时再 `understand-user` 与 `maintain-memory` | 记录已处理来源版本与实际写入的修订；材料不可访问则保留待核实。 |
| 助理对话回合落盘 / 用户纠正 / 用户要求遗忘 | `understand-user` → 记忆增量整理；纠正和遗忘优先处理 | 新摘要和专题版本一致，旧来源不能在补扫后复活被删除内容。 |
| 子代理完成、失败、待审批或结果未知 | `delegate-and-verify` 核验返回 → 必要时重新评估工作与更新台账 | 仅“有证据完成”能关闭承诺；未知外部结果不自动重放。 |
| App 活跃期间的每日检查 | `follow-up` 检查期限、阻碍和过期状态；可能触发 `reflect-and-suggest` | 每个本地自然日最多一次有效检查，无新信息可无用户可见输出。 |
| App 活跃期间的每周检查 | 复盘目标变化、长期阻碍和协作反馈 | 每个本地自然周最多一次有效回顾，不补发关闭 App 期间的多个错过周期。 |
| 已配置来源的同步游标变化 | 读取变化摘要并入来源队列；专业读取由授权子代理处理 | 记录来源的新版本和最后成功同步时间，未配置的账号与目录不扫描。 |

每个队列项有 `jobId`、任务种类、触发原因、来源 ID 与版本、受众范围、创建和到期时间、去重键、状态、失败原因、重试时间、成本预算、相关会话/委派 ID。状态至少区分 `queued`、`running`、`waiting`、`completed`、`failed`、`cancelled`；完成标记与文件修订要按可恢复顺序提交。重启时只重排尚未完成的幂等内部任务；对外部副作用先查询既有运行/投递结果。过时来源版本的任务合并，新版本重新评估；审阅记录、记忆修订和建议自身不构成新的独立来源，避免循环。

调度优先级：用户当前消息与其等待的子任务在前；纠正/遗忘与身份撤销其次；有期限的核验，再到工作评估、记忆整理、每日/每周回顾。前台压力升高时暂停后台模型调用，不丢队列。纯状态校验尽量不用模型；模型任务限制并发、输入、耗时和费用。被取消的模型输出不得在稍后落盘。App 完整退出时有界停止 Worker 与子代理；下一次启动合并错过的周期，不在关闭期间工作。安静时段约束主动投递，不阻止本地内部整理。

## 主动性的实际边界

助理可以自动更新自己的 `memories/`、`work/` 与 `reviews/`，在已授权来源内检索，并通过有范围的子代理做只读核验。文件修改、发布、对外联系等专业执行仍按对应宿主权限和用户已有授权处理。建议、评估发现和整理进度归助理页面；Work 对话仅承载当前工作回答。企业微信普通回复回到原会话，主动推送依配置与投递状态单独处理；没有可靠已读回执就保持未知。

例如用户在 Work 中说“这项任务已经完成”，随后工具结果显示缺少一个产物：事件触发 `review-work` 记录“部分完成”和缺失证据；`organize-work` 留下待核实事项；若可授权只读检查，`delegate-and-verify` 请求子代理核对产物。助理收到证据后更新状态，必要时在助理页面提醒用户。工作对话不插入这条主动提醒，也不把用户的一句“完成了”改写成事实完成。
