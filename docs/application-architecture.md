# YuanpuAgent 总体架构

更新：2026-09-22。本文记录本轮讨论收敛的目标架构，不代表相关模块已经实现。实现状态和验收记录仍以代码及 `.tasks/tasks.yaml` 为准。

## 1. 产品定位与确定的边界

YuanpuAgent 是运行在用户电脑上的 Pi 工作助手。桌面对话、IM 消息和定时任务是同一个本机 Agent 的不同入口；模型请求使用用户配置的服务，文件操作与本机工具在用户电脑执行。

- 全部运行能力跟随 Electron App 生命周期。启动 App 后工作，退出 App 后停止；不安装独立后台服务，不提供 App 退出后的执行保证。
- IM 用于远程操作本机 YuanpuAgent，不建设云端 Agent 或多租户执行平台。
- 复用 `packages/yuanpu-runtime` 和 `packages/yuanpu-protocol`，保持 Pi 上游包不变。
- 外部能力继续通过两个 Yuanpu MCP 元工具发现和调用；Python 保持独立能力进程。
- 用户侧沿用“技能”作为能力分发概念，连接账号和定时任务是使用技能的产品功能。
- 根目录 `server/` 保持技能市场职责，不承担机器人执行和本机调度。

本文取代先前讨论中的独立常驻服务、系统服务安装和云端 Gateway 作为首版基础的建议。平台接入方式需要公网回调时，应单独评估，不直接公开本机 Runtime API。

## 3. 运行结构

```text
Electron App（唯一生命周期管理者）
├── React 界面：对话、连接、任务、技能、设置
├── 宿主能力：系统通知、点击导航、运行状态
└── SEA Runtime
    ├── Channels ──────────── IM 入站消息
    ├── Scheduler ─────────── 到期任务
    ├── AgentService ←─────── 桌面对话
    │   └── Pi 会话 → Pi 内置工具 / Yuanpu MCP 元工具
    ├── CapabilityHost ────── MCP / Python / 外部工具
    ├── Notifications ─────── 请求 Electron 展示通知
    └── 本机持久化 ────────── 计划、运行记录、去重、投递状态
```

IM 和 Scheduler 统一向 AgentService 提交任务。普通回复由宿主按可信路由发回原会话；模型无需自己选择接收者。需要主动向其他会话发送消息时，再通过受权限控制的能力调用。

```text
apps/
├── app/                       # React 管理和对话界面
├── desktop/                   # Electron、Runtime 管理、系统通知
├── runtime/                   # SEA 入口、HTTP/事件传输、模块装配
└── python-capabilities/        # 内置 Python MCP 能力

packages/
├── yuanpu-runtime/src/
│   ├── agent/                 # AgentService、会话映射、排队与取消
│   ├── channels/              # 连接管理、身份映射、消息与投递
│   │   └── adapters/          # 首批内置 IM 平台适配器
│   ├── scheduler/             # 计划、时区、触发与漏跑策略
│   ├── notifications/         # 通知请求、偏好、合并与去重
│   ├── persistence/           # Yuanpu 运行状态及迁移
│   ├── capabilities/          # 现有 MCP 与授权
│   ├── packages/              # 现有能力包安装与配置
│   ├── config/                # 现有配置和用户目录
│   └── pi/                    # 现有 Pi 公开接口适配
├── yuanpu-protocol/            # 桌面与 Runtime DTO、事件和版本契约
└── …                          # Pi 上游包，按上游同步规则维护
```

目录是责任划分，不要求每项成为独立进程或 npm 包。首批渠道适配器随 Runtime 发布；独立安装连接器的清单、依赖隔离与加载协议留给后续实际需求。

## 5. App 生命周期

启动顺序：校验/激活暂存 Runtime → 初始化持久化 → 恢复会话映射和未完成记录 → 建立宿主事件连接 → 开启 IM 与调度 → 界面就绪。

退出顺序：停止接收新任务与触发计划 → 有界等待当前执行 → 取消剩余执行并记录中断 → 关闭渠道与 MCP 子进程 → 刷新持久化 → Electron 退出。取消不代表撤销已经发生的外部操作。

Runtime 崩溃时，Electron 展示状态并按有限退避策略重启；同一 App 实例不得重复启动 Runtime。Electron 异常退出时，Runtime 必须通过父进程存活检测或平台进程归属机制退出，并清理受管子进程。不能仅依赖 `before-quit`。

“关闭窗口”与“退出 App”必须明确区分。托盘驻留是可选产品行为，尚未作为默认交互确认；若支持，界面必须可见地说明 App 仍在运行，并提供明确退出入口。无论窗口策略如何，App 退出后所有运行能力停止。

## 6. 会话与统一执行

AgentService 提供提交任务、订阅执行事件、查询记录、取消任务和继续会话的窄接口。请求至少包含入口、宿主确认的身份、工作区、会话引用、输入内容和幂等键；结果包含 runId、状态、输出及目标路由引用。

- IM 默认按渠道类型、连接账号、会话与线程隔离。发送者身份用于权限检查，不能由消息正文或模型声明替代。
- 桌面可查看和继续 IM 会话；共享已有会话必须显式绑定。
- 同一会话串行执行；跨会话设置并发上限及有界队列。
- 定时任务默认独立会话，可显式关联既有会话。
- Pi 管理对话内容；Yuanpu 保存外部会话到 Pi 会话的映射及任务记录，避免复制一套对话存储。
- 显式选择远程会话可用的工作区、工具和记忆范围；不把所有本机配置自动传入任何群聊。

执行记录区分 queued、running、waiting_approval、succeeded、failed、cancelled、interrupted/result_unknown。重启只能恢复可证明安全的步骤；不承诺任意 Agent 执行的透明断点续跑。

## 7. IM 渠道

适配器负责连接与身份验证、平台事件转换、附件转换、发送回复、断线恢复及平台限流。共用层负责去重、配对、会话路由与投递记录。

统一入站消息包含 connectionId、conversationId、threadId、messageId、senderId、内容块及接收时间；平台特有字段保留为适配器元数据。消息先可靠接收/记录再按平台协议确认，避免模型处理时间阻塞事件接收。

首版按单机单用户配对可信 IM 账号；群聊需要明确的触发成员与触发条件。私聊、群聊、线程及账号之间不得串消息。平台能否补收离线消息必须按具体接入方式验证，不能统一承诺。

2026-09-23 范围决策：当前产品按“个人助手”验收，首发企业微信只要求一位获授权用户与机器人私聊；不以第二名真人或真实群聊作为阶段完成门槛。同一用户的桌面、私聊、计划等入口仍须保持身份、会话与投递目标正确，重复事件、断线/退出恢复和未知发送仍须验证。未配对身份拒绝和跨会话隔离保留自动化/隔离 fixture 回归，不因单用户定位放宽权限。多成员、群聊和第二真实会话属于后续显式扩展，不能把单私聊成功写成那些场景已通过。此决定调整 TASK-019 及后续未完成的渠道验收口径，不改写 TASK-018 的历史实施证据。

首发固定为企业微信“智能机器人 API 模式 + WebSocket 长连接”，不是仅出站通知的群机器人 Webhook，也不是要求公网 URL 的传统应用回调。TASK-017 固定官方契约与验证环境，TASK-018 实现首个 adapter；凭据只以 Bot ID/Secret 引用进入 SecretStore，SDK 必须注入脱敏 logger，不记录消息正文、附件 URL/AES key 或完整帧。

腾讯微信 ClawBot 作为第二阶段渠道，在企业微信完整业务验收后推进。由于官方参考实现是 OpenClaw ChannelPlugin，而 Yuanpu 运行 Pi Runtime，不能把插件可运行等同于可直接接入。先由 TASK-023 决定 Yuanpu 自有 adapter、代码复用或受管网关的边界，并验证二维码凭据、iLink 长轮询、context token、本地引用/媒体缓存和版本兼容；再由 TASK-024 实现、TASK-025 独立验收。ClawBot 不阻塞企业微信首发，也不复用企业微信的真实平台验收结论。

## 8. 定时任务与可靠性

Scheduler 只负责时间计划和产生到期执行；AgentService 负责执行，Channels 负责结果投递。首版支持单次任务、周期计划、时区、启停、执行历史和输出目标。

使用本机 SQLite 保存计划、执行记录、消息去重及待投递结果。具体驱动需在 Node 24 SEA 构建中验证后选择。计划变更、唯一触发键与执行入队须通过事务保持一致。

- 以计划 ID、计划修订号和预定触发时间生成唯一键，避免重复扫描入队。
- 每项计划明确时区；存储执行时间点使用 UTC。夏令时跳过和重复时刻需有确定策略。
- 默认不重叠执行。App 再打开或电脑唤醒后，默认合并补跑一次，可配置跳过并设置最大迟到时间。
- 未开始任务可恢复排队；已开始但结果未知的任务先标记状态，不能整段自动重跑。
- 模型执行成功后单独持久化回复，投递失败只重试投递；下游支持时传入幂等键。
- 配置执行超时、队列上限、重试上限与历史保留策略。

本机关机、睡眠或 App 退出期间不能保证准点执行。App 重新运行后的恢复能力是首版可靠性的范围。

## 9. Electron 系统通知

Electron 主进程通过原生通知接口展示提醒；Runtime 不导入 Electron。系统事件和 Pi 主动提醒复用同一个通知路由。

Pi 通过 `search_capabilities` / `execute_capability` 使用 `notify_user` 能力；任务完成、失败等宿主事件直接提交通知请求。Runtime 到 Electron 的事件连接由 Electron 主进程建立，可采用带认证的 SSE，并按事件 ID 去重；renderer 只通过 preload 获取必要状态。

通知请求包含 requestId、标题、正文、类型和可选的 conversationId/runId。Electron 返回 submitted、suppressed、unavailable 或 failed 等处理结果。系统接受通知不等于用户实际看到，结果不得声称已阅读。

用户点击通知时打开或聚焦 App，并导航到宿主验证过的会话或任务；不执行通知内容提供的任意命令或 URL。支持开关、隐私预览及同一任务提醒合并。系统权限不足或勿扰时，应用内记录仍可查询。

Python 示例弹窗保持独立：弹窗是工具交互，Electron 系统通知是产品提醒。不通过 Python 替代 Electron 通知。

## 10. 权限与凭据

保留现有审批机制，新增可配置的自动批准策略，减少可信本机工作中的重复确认。模式由用户设置，模型和远程消息不能修改自身权限。

“完全访问”是否覆盖所有应用内逐次审批尚待产品决策；若保留高风险确认，名称必须体现真实范围。此模式不绕过操作系统权限。任务和已配对渠道明确绑定执行策略，不能把任何群成员自动视作本机所有者。

MCP 审批仅覆盖 Yuanpu 能力入口。当前 Pi 内置 bash/read/write/edit 和直接加载的扩展需要纳入权限评估；扩展与 Runtime 同权限，不构成安全沙箱，不能将 MCP 审批宣称为全进程隔离。

后台执行遇到缺失权限时进入等待授权，并记录原因和到期策略；App 退出后重新打开需重新校验执行上下文与授权，不复用已消费的一次性授权。

配置保存凭据引用；沿用现有环境变量方案，系统凭据存储可后续接入。通知内容、日志和会话记录应按用途最小化记录凭据及敏感数据。

## 11. 用户数据与升级

```text
~/.yuanpu/
├── app/
│   ├── config.json             # 全局与提醒偏好
│   └── channels/               # 内置渠道配置及凭据引用
├── agent/                      # Pi settings/auth/models、会话、skills、memory
├── packages/                   # 已安装能力包及独立配置
└── workflows/
    └── automation.sqlite       # 计划、会话映射、运行记录、去重和投递
```

数据库内部按模块分表，Yuanpu 业务状态由 Runtime 单进程写入。后续市场渠道的包配置使用已有 `packages/config` 规则，通过连接实例引用，避免重复保存。

保留 Electron 与 SEA 分别发布、SEA 下载校验暂存及下次 App 启动激活的机制。Electron 是唯一 Runtime 版本切换负责人；App 运行期间不热替换正在执行的 Runtime。

升级必须检查宿主协议兼容性，健康检查失败回退旧二进制；数据库迁移优先采用向后兼容的增量变更。不可逆迁移需独立设计备份及恢复，不能仅依赖二进制回滚。现有 Runtime 二进制保存位置无需随本轮设计迁移。

## 12. 实施阶段与验收

1. **会话与生命周期基础**：提取 AgentService、会话映射、队列与取消；验证已有桌面对话回归、会话隔离、退出清理和崩溃处理。
2. **系统通知闭环**：实现宿主事件通道与 notify_user；验证 Pi 调用、系统事件提醒、重复事件、通知不可用及点击导航。
3. **一个 IM 渠道闭环**：确定接入类型，完成配对、收发、会话续接、取消和重连；验证错误身份、重复消息和 App 退出后的离线行为。
4. **持久定时任务**：接入统一执行与结果投递；验证重启、睡眠恢复、时区、漏跑、执行中断和发送失败。
5. **产品与发布验收**：完善连接、任务和权限设置；运行跨平台打包、SEA 升级与数据兼容测试，再逐步增加平台。

本轮更新架构文档、导航和任务卡，不实施功能，不提交或推送。任务依赖及实时状态以 `.tasks/tasks.yaml` 为唯一来源；原有 Python 专项任务及发布缺口保持独立。

## 13. 管理界面提案与任务导航

以下是建卡阶段的文字交互提案，尚无视觉方案批准记录。沿用现有侧栏和对话页面，新增“连接”“定时任务”入口；提醒偏好放在设置中，执行结果仍可回到对应会话查看。

- 连接：列表显示账号与连接状态，详情编辑配置并测试连接；失败保留输入，成功返回连接详情。配对身份与允许的群触发规则明确显示。
- 定时任务：列表展示启停、下次时间和最近结果；编辑面板填写指令、工作区、时间/时区与输出目标，保存前预览下一次执行。运行详情展示输出、投递状态和关联会话。
- 对话：展示桌面、IM 或计划来源和执行状态，提供取消及等待授权入口；不将连接器内部类型作为用户主导航。
- 提醒：设置开关与预览偏好；点击系统通知定位到已有会话/run，无效或过期目标返回可理解提示。
- 必须覆盖空列表、加载、离线、错误、排队、等待授权、执行中和完成状态。数据与错误来自真实 Runtime 契约。
