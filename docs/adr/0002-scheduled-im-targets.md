# 0002 — 定时任务的企业微信私聊目标

状态：实施中（TASK-026，2026-09-23）。首版仅面向已配对的个人私聊；群聊和多成员主动推送不在本决策范围。

## 决策

企业微信入站回复使用一次性 `req_id`，不能作为定时任务的长期发送路由。官方 SDK 的主动发送以单聊成员 `userid` 为目标；因此 Runtime 只从已认证、已配对的私聊入站观察候选联系人。客户端通过本机 Bearer 认证的 `GET /v1/channels/schedule-targets` 取得不透明 `contactId`，再以 `POST` 显式绑定，获得不透明 `routeId`。建计划时只能引用这个仍有效的 `routeId`，不能提交原始 `userid` 或任意路由充当授权。

SQLite schema v5 在受保护的本机元数据文件中保留配对私聊的最小目标映射：连接、sender 摘要、原始 `userid`、最后观察时间及可撤销的随机目标引用。API、日志、任务记录和通知不返回原始标识。`DELETE /v1/channels/schedule-targets/{routeId}` 先使引用失效、清除原始目标，再等待已启动发送落定；重新收到消息后如需投递，必须显式生成新引用。解除配对会删除映射，旧计划不会自动指向新身份。现有 `pairedSenderDigests` 配置只引导新增配对，删除配置项不会撤销已持久配对；撤销计划投递必须使用上述解绑接口。连接的 Bot/凭据绑定沿用不可原地变更的现有保护。

调度只在通道启动后首次扫描。鉴权前的发送没有写出，保持 `pending` 且不消耗尝试次数；明确拒绝记 `failed`；可能已写出的超时/断线记 `result_unknown`。官方主动发送未提供幂等键，故失败和未知都不自动重发，更不重新执行 Agent。App 退出先关闭调度、再关闭渠道，以终止新发送。系统通知的宿主回执与 IM 投递分别在 SQLite 记录并可由计划历史查询；宿主回执 `submitted` 只证明交给操作系统，不证明用户已看到。未完成的通知回执在重启后记 `result_unknown`，不自动重新弹出。

## 边界

`GET` 的候选联系人只是本机观察事实，不等于用户已授权投递；`POST` 才是绑定动作。SQLite 文件受现有 0600 权限保护，但不是加密保险库，也不承诺物理擦除 WAL；若后续产品要求更强的数据保留或擦除保证，须单独设计。真实企业微信展示、连接配置和 Electron 点击仍由独立的通知渠道与调度阶段验证（TASK-019）验收。
